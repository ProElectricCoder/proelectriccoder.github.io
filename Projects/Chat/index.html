01 / Overview

Architecture

The engine splits communication into two layers: signaling (finding the other peer and swapping connection details) and data transfer (an RTCDataChannel). Once the channel is open the signaling service is no longer involved. Every message travels directly between browsers, or through a TURN relay when a direct path is impossible.

The three engines share one interface, so the app can swap them without changing how it sends or receives. They differ only in how the first handshake happens.

On top of them sits Peer, a PeerJS-style layer: one call to host a room, one call to join, one Connection object per remote peer, standard events, automatic reconnect. It is the simple tier. The engines are the advanced tier: you drive signaling, relay and media yourself. Both live in engine.js and the advanced tier is fully backward compatible, so existing apps keep working unchanged.

02 / Simple API

Quick Start: the Peer API

Peer wraps an engine. Host a room or join one, and you get Connection objects that work like small event emitters. It signals through Cloudflare by default (you pass a Firebase ID token) or through Firebase (you pass a Firestore handle). 

import { Peer } from '/Projects/Chat/engine.js';

const token = () => firebase.auth().currentUser.getIdToken();   // a string, or an async function

// Host: resolves once signaling is open and guests can join
const host = await Peer.host('my-room-123', { token, id: 'alice' });
host.on('connection', conn => {
  console.log(conn.peer, 'joined', conn.metadata);
  conn.on('data', msg => console.log(conn.peer, msg));
  conn.on('close', ({ reason }) => console.log(conn.peer, 'left:', reason));
});
host.send({ type: 'announcement', text: 'Welcome' });          // to every guest

// Guest, in another browser: resolves once the host answered and the channel is open
const guest = await Peer.join('my-room-123', { token, id: 'bob', metadata: { name: 'Bob' } });
guest.on('message', ({ from, data }) => console.log(from, data));
guest.send({ type: 'chat', text: 'Hello!' });                  // to the host

Reconnect policy

Guests. When the channel dies, the connect times out or signaling fails, the Peer waits baseMs × 2attempt−1 (capped at maxMs) and joins again with a fresh engine and a fresh token. The Connection object stays the same, so your handlers stay attached: it emits reconnecting, then open again. After retries failed attempts, join() rejects (if it never connected) or the Peer closes with reason 'lost'.

Hosts. A lost signaling socket is re-opened the same way, and guests that are already connected are unaffected. A guest that reconnects reaches the host as a new Connection (a new connection event, and peer-left for the old one) with the same conn.peer.

Clean exits do not retry. disconnect() and conn.close() send a goodbye frame first, so the other side closes with a reason instead of reconnecting. Frames whose __peer field is a string are the Peer layer's own hello and goodbye frames; avoid that field name in your data.

Error types

error.typeMeaning
authNo token, or the token function threw. A missing token is thrown by host() and join() before anything connects.
signalingThe signaling server is unreachable, or a Firestore stream broke.
timeoutThe host did not answer within connectTimeoutMs, or signaling did not open in time.
connection-lostA guest lost the host and used up its retries.
unavailableNo WebRTC in this browser, no room name, or a Peer that was already used. A Peer is single-use: make a new one.

Debugging, and your own signaling

const peer = await Peer.join('my-room-123', { token, debug: true });   // also logs to console.debug
console.table(peer.getTrace());                                         // last 200 entries: [{ t, msg }, ...]
peer.on('route-change', ({ peer: id, relayed }) => console.log(id, relayed ? 'TURN relay' : 'direct'));

// Bring your own signaling: return anything that implements the shared engine interface
const custom = new Peer({ createEngine: opts => new MyEngine(opts) });

The interface is createRoom, joinRoom, send, sendTo, closePeer, disconnect, the on… callbacks (onMessage, onPeerConnected, onPeerDisconnected, onRoute, onTrack, onError) and a peers map. onSignaling and reconnectSignaling are optional.

What the simple tier leaves out on purpose: guests only talk to the host (use new ChatEngine({ relay: true }) for a transparent group relay), and media is not negotiated for you (the engines negotiate once, at connect time). Reach the engine with peer.engine when you need either.
03 / Firebase Mode

ChatEngine

ChatEngine uses Firebase Firestore as a rendezvous server. The host listens to signals for new offers, and each guest writes one document under its own id. ICE candidates are trickled into that document as they appear, including slow TURN relay candidates.

Prerequisites: The host page must call firebase.initializeApp(config) and pass firebase.firestore() to engine.init() before calling any room methods. 
import { ChatEngine } from '/Projects/Chat/engine.js';

// Assumes firebase.initializeApp() already called on this page
const engine = new ChatEngine();
engine.init(firebase.firestore());

// Register callbacks before joining
engine.onPeerConnected(peerId => console.log('peer joined:', peerId));
engine.onPeerDisconnected(peerId => console.log('peer left:', peerId));
engine.onMessage((data, peerId) => console.log('message from', peerId, data));

// Host: create a room
await engine.createRoom('my-room-123');

// Guest: join the same room
await engine.joinRoom('my-room-123');

// Once onPeerConnected fires, send data
engine.send({ type: 'chat', text: 'Hello!' });
04 / Cloudflare Mode

CloudflareWSEngine

CloudflareWSEngine swaps Firestore for a WebSocket to a Cloudflare Durable Object. Signals arrive instantly instead of through snapshot listeners. It always connects to CF_WS_URL (wss://proelectriccoder.pages.dev/api/ChatRooms); a URL passed to the constructor is ignored. Each room request carries a Firebase ID token, which the server checks.

Signals sent before the socket opens wait in an outbox, and the socket reconnects with backoff. The host keeps its socket open for new guests. A guest only needs it until its channel is open. Pass token as an async function and the engine fetches a fresh token on every reconnect. 

import { CloudflareWSEngine } from '/Projects/Chat/engine.js';

const engine = new CloudflareWSEngine();
const token = () => firebase.auth().currentUser.getIdToken();   // string or async function

engine.onMessage((data, peerId) => console.log(peerId, data));
engine.onRoute(({ peerId, relayed }) => console.log(relayed ? 'TURN relay' : 'direct P2P'));

await engine.createRoom('my-room-123', token);   // host
await engine.joinRoom('my-room-123', token);     // guest

Two hooks show what the socket is doing. onSignaling reports its state, and onError reports problems the engine used to only log. After 'failed' (the built-in six backoff tries are used up), reconnectSignaling() starts over with a fresh budget. Peer does all of this for you. 

engine.onSignaling((state, info) => console.log('signaling', state, info));   // connecting | open | reconnecting | failed | closed
engine.onError(({ code, error }) => console.warn(code, error));                // offer | signaling-stream | token | websocket | signal
if (!engine.reconnectSignaling()) console.log('no room to reconnect to');
05 / Direct Mode

DirectEngine

DirectEngine generates SDP strings that you exchange with the remote peer through any channel: paste them in a chat, email them, show them as QR codes. No server, no sign-in, no dependency other than a modern browser. It is a single-peer engine, so there is no createRoom and the peer id passed to callbacks is always 'remote'.

Slow to build, on purpose: the SDP has to contain every ICE candidate, so createOffer() and createAnswerFor() wait up to 6 seconds for gathering to finish. That includes TURN relay candidates. 
import { DirectEngine } from '/Projects/Chat/engine.js';

// ── Caller side ─────────────────────────────────────────
const caller = new DirectEngine();
caller.onMessage(data => console.log('received:', data));
caller.onPeerConnected(() => console.log('connected!'));

const offerSDP = await caller.createOffer();
// Display offerSDP to user — they copy/share it to callee

// After callee sends back their answer SDP:
await caller.setAnswer(answerSDP);

// ── Callee side ─────────────────────────────────────────
const callee = new DirectEngine();
callee.onMessage(data => console.log('received:', data));

const answerSDP = await callee.createAnswerFor(offerSDP);
// Display answerSDP to user — they share it back to caller
06 / Connectivity

STUN, TURN and Route Detection

Every engine builds its RTCPeerConnection from getIceConfig(): public STUN servers to find each peer’s address, plus a free public TURN relay (Open Relay Project) that only carries traffic when no direct path exists. After connecting, monitorPC inspects the selected candidate pair and calls onRoute, so the app can show direct P2P or TURN relay in the status line.

A brief “disconnected” state is normal when a network changes, so a peer is dropped only after 8 seconds of it (graceMs), or at once on failed or closed. A ping every 5 seconds also removes a peer whose channel has been silent for 10 seconds. Any incoming frame counts as proof of life, not only a pong, so a busy peer in a throttled background tab is not dropped. All three timings are options: heartbeatMs, timeoutMs and graceMs. 

// Add your own TURN server without touching the code (checked before the built-in list)
localStorage.setItem('pec_ice_servers', JSON.stringify([
  { urls: 'turn:turn.example.com:3478', username: 'user', credential: 'secret' }
]));

// Route info, for any engine
engine.onRoute(({ peerId, relayed, local, remote }) => {
  // local / remote are candidate types: 'host' | 'srflx' | 'prflx' | 'relay'
});
Shared TURN: the built-in Open Relay credentials are public and rate-limited. Use your own TURN account for anything that matters.
07 / Groups

Group Chats — Host Relay

Groups use a star topology. Members connect only to the host. When the host’s engine is created with { relay: true } it forwards each incoming frame to every other peer before handing it to its own onMessage. Receivers filter on the message’s own to field, which is how one frame can be addressed to a single member.

The relay copies raw frames and never looks inside them, so any new message type works in groups with no host changes. It also means the host can read plain-text messages unless the chat is encrypted. 

const host = new CloudflareWSEngine({ relay: true });   // also accepted by ChatEngine

09 / Examples

Usage Examples

Collaborative code editing

engine.onMessage((msg) => {
  if (msg.type === 'edit') {
    editor.applyDelta(msg.delta);
  }
});

editor.onChange(delta => {
  engine.send({ type: 'edit', delta });
});

Sending binary data (file transfer)

// Sender
const buffer = await file.arrayBuffer();
engine.send(buffer);  // ArrayBuffer sent as binary frame

// Receiver
engine.onMessage(data => {
  if (data instanceof ArrayBuffer) {
    const blob = new Blob([data]);
    saveBlob(blob);
  }
});

The Chat App itself sends files as a file-meta message, then file-chunk messages, then file-done.

10 / Data

Data Types

The engine transparently serialises and deserialises data so you can work with native JS types.

Sent asReceived asNotes
string string Passed through as-is. A JSON parse is attempted on receive and falls back to the string.
object / array object / array Serialised with JSON.stringify, parsed on receive.
ArrayBuffer ArrayBuffer Sent as a binary WebRTC frame. No JSON serialisation.
Uint8Array / other typed arrays object (broken) Not binary-safe: they are JSON-serialised like any object. Send u8.buffer.slice(u8.byteOffset, u8.byteOffset + u8.byteLength) instead.
Blob ArrayBuffer Sent natively. The channel’s binaryType is 'arraybuffer', so it arrives as an ArrayBuffer.
number / boolean number / boolean Converted with String(), then parsed back. A string such as "42" also comes back as a number, so wrap values in an object when the type matters.
11 / Firestore

Firestore Schema

chatRooms is used only for signaling. Once connected, it is idle. The Chat App adds a second collection, chatIds, that maps a readable Chat ID to an account. 

chatRooms/ (collection)
└─ {roomId}/ (document)
   ├─ createdAt: Timestamp
   ├─ host: true
   └─ signals/ (subcollection)
      └─ {guestId}/ (one document per guest)
         ├─ type: "offer"
         ├─ sdp: "<offer SDP string>"
         ├─ createdAt: Timestamp
         ├─ guestCandidates: ICECandidate[]   (written by guest, grows as ICE trickles)
         ├─ answer: "<answer SDP string>"        (written by host)
         └─ hostCandidates: ICECandidate[]    (written by host)

chatIds/ (collection, Chat App only)
└─ {chatId}/ lower-cased, e.g. google-you@gmail.com
   ├─ uid: "<Firebase UID>"
   ├─ provider: "google.com" | "github.com" | "password"
   └─ claimedAt: Timestamp
In production, add Firestore security rules to restrict who can read and write room signals. The rules for chatIds are in FIRESTORE_RULES.md.
12 / Production

Production Checklist

The demo path works on a laptop. These are the things that decide whether it keeps working for other people.

AreaWhat to do
Firestore rulesFirebase signaling needs rules for chatRooms. The repo only documents the chatIds rules, so the room rules live in your Firebase console. If you are starting fresh, the snippet below is the minimum: it only requires sign-in.
AuthPass token as an async function so reconnects get a fresh one. The Cloudflare relay verifies the Firebase ID token and answers 403 to password accounts whose email is not verified.
Room namesNeither signaling path decides who may join a room beyond requiring sign-in. Use unguessable room names (Peer.makeId() works) and check membership in your own message protocol.
TURNThe built-in Open Relay credentials are public and rate-limited. Add your own through pec_ice_servers; Peer picks it up automatically. Watch route-change to see how many links end up relayed.
Browser supportNeeds RTCPeerConnection, RTCDataChannel and ES modules. The code uses optional chaining, so the floor is roughly Chrome and Edge 80, Firefox 72 and Safari 13.1. Check Peer errors of type unavailable.
Message sizeKeep a single send under about 256 KiB and chunk anything bigger, as the Chat App does with file-meta, file-chunk and file-done. Older browsers are only safe at 16 KiB. Typed arrays must be sent as an ArrayBuffer.
Graceful exitCall peer.disconnect(), for example on pagehide. The other side then closes with a reason. Without it, a host waits for 10 seconds of silence and a guest goes through its reconnect attempts.
Sleepy tabsBrowsers throttle timers in background tabs. Since 1.5.0 any incoming frame counts as proof of life, but for apps where tabs sleep for long periods raise timeoutMs.
Stale roomsFirebase mode never deletes chatRooms or signals documents. Both carry createdAt, so add a Firestore TTL policy on it, or sweep them from a scheduled function. Cloudflare rooms leave nothing in Firestore.
ObservabilitySubscribe to error, reconnecting and route-change, and attach peer.getTrace() to bug reports.

A minimal rules block for Firebase signaling (tighten it for your own data model):

match /chatRooms/{roomId} {
  allow read, write: if request.auth != null;
  match /signals/{guestId} {
    allow read, write: if request.auth != null;
  }
}

14 / Reference Apps

Reference Apps

Three apps in this repository run on the same engine.js. They use the advanced tier on purpose: they predate Peer and rely on relay or raw channels. Read them as worked examples of the engines.

Chat App

The widest tour: all three engines, 1:1 chats and groups with a relay: true host, a message protocol on top, and call signaling carried over the chat’s own channel.

DeepBlue IDE collab

A CloudflareWSEngine whose host relays, so guests see each other’s edits. Yjs updates travel as ArrayBuffer frames, and both sides announce on every connect so a rejoining peer catches up.

Cards game

A host that is the authority and does not relay. It deals each player a private hand with engine.sendTo(), so one player’s cards never travel to another.

Moving an app from the engines to Peer

For a new app with one host and several guests that need ids, reconnect and typed errors (lobbies, shared cursors, small games), start with Peer. The mapping from the engine calls is direct:

Engine callPeer equivalent
engine.createRoom(room, token)Peer.host(room, { token })
engine.joinRoom(room, token)Peer.join(room, { token })
engine.onMessage((data, peerId) => …)peer.on('message', ({ from, data }) => …)
engine.onPeerConnected(id => …)peer.on('connection', conn => …) on the host, await Peer.join() on a guest

15 / Chat App

The Chat App version 4.0.0

The app lives in /Projects/Chat/App/: plain ES modules, no bundler. It uses the engines above and adds everything a chat needs on top.

Chats

1:1 over Direct, Firebase or Cloudflare, and groups with a host relay. Readable Chat IDs: google-…, github-…, email-….

Messages

Replies, reactions, edit and delete for everyone, and polls where votes can be changed and are visible.

Find things

In-chat search with highlights, pinned messages, personal stars, and a library of media, files and links.

Voice and files

Voice messages with a waveform, chunked file transfer with previews, and link previews through an Open Graph function.

Calls

1:1 voice, video and screen sharing, plus group calls. Call signaling travels over the chat’s own channel.

Awareness

Delivered and read ticks, “Seen by” in groups, typing indicators, browser notifications, per-chat mute.

Privacy

Optional password-based AES-GCM encryption of message content, and disappearing messages: 5 minutes to 7 days, removed on every device.

Backup

Optional Google Drive backup and restore of chats, with expired messages never included.

Message protocol

Everything the app sends is one JSON object with a type. The host relay forwards unknown types untouched, so new ones work in groups automatically.

typePurpose
chatA text message. Carries a shared id, the author id aid, an optional reply and the chat’s ttl.
msg-delivered · msg-readReceipts for a message id.
msg-react · msg-pin · msg-edit · msg-deleteChanges to an existing message. Only its author may edit or delete.
poll · poll-vote · poll-closeCreate, vote on (and change a vote on) and close a poll.
chat-ttlSet the disappearing-message timer: 0, 300, 3600, 86400 or 604800 seconds.
file-meta · file-chunk · file-doneA file or voice message, sent in pieces.
typing · typing-stopTyping indicator.
call-logCall card, with the call’s SDP and ICE in its meta.
gc-*Group call invite, accept, offer, answer, ICE and end.
handshake · group-members · display-nameNames, avatars and the member list.
Limits worth knowing: edits, deletes and timers only reach peers who are online. In groups the author id is asserted by the sender’s client. Disappearing messages cannot stop screenshots.
